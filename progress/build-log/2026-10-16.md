# Build log — 16 October 2026

## Page freeze, crash and blinking during a long document

Report from the owner's manual test: while `05-subscription-booklet-long.docx` was processing, the Intake page stopped responding, Chrome then showed "This page is having a problem" (`Crashpad_HandlerDidNotRespond`), and the page sometimes blinked when opened.

### What was found

- **The laptop was out of memory.** Commit charge was 31.3 of 31.7 GB, and the worker process (`uvicorn app:app`) held 17.7 GB of committed memory with 1,245 threads, of which only 33 MB was resident. In a separate Chrome instance on the same machine, model decoding failed with `WebAssembly.instantiate(): Out of memory`, and the WebGL context was lost while switching screens. Both match the hang, the crash and the blinking.
- **Cause: one new thread per worker job.** PyTorch keeps a native thread pool for each thread that calls it, and those pools are never released. A standalone check with the worker's Python and torch went from 19 to 349 threads after 30 jobs on fresh threads, and from 19 to 31 when the same 30 jobs ran on one shared thread.
- **Browser side, also fixed:**
  - Every job progress update after the first finished step re-read all of the version's data (723 blocks and 555 annotations for the long booklet), and those reads could overlap.
  - The lens "glass" material used a transmission pass, which re-renders the whole canvas with mipmaps every frame.
  - If the GPU dropped the context, there was no fallback.
  - The still image was hidden before the 3D model had drawn, and again after each fly-in animation.
  - The WebGL support probe left an extra context open.
  - Per-station materials were never freed.

### Changes

- `worker/app.py`: all model work (loading and every prediction) now runs on one dedicated thread (`laya_thread`), which replaces `laya_lock`.
- `src/lib/workspace.tsx`:
  - Progress updates only replace the job row. The version's data is re-read when a step finishes or the job ends, and only one read runs at a time.
  - Decisions are fetched by joining on the version instead of sending a URL that lists every finding id.
  - The recent-documents list refreshes at most every 3 s.
- `src/components/three/Stations.tsx`, `hub/StationArt.tsx`, `App.tsx`:
  - No transmission anywhere, including materials carried in the GLB files.
  - Device pixel ratio capped at 1.5.
  - On `webglcontextlost`, the page switches to the still images.
  - A station counts as ready only after it has drawn three frames, and the still shows again after a fly-in.
  - Materials are disposed on unmount, and the WebGL probe context is released.

### Checks run

- `npx tsc --noEmit`: clean. `python worker/test_sanitize.py`: ok. `python worker/test_semantic_quota.py`: ok.
- Worker restarted with the fix. The long booklet was re-run end to end through the local app (4 min 10 s, 17 findings, 66 input fields, 555 paragraph regions). Afterwards the worker had 50 threads and 4.5 GB, mostly the two loaded models; it started the run at 48 threads.
- Browser during that run (development build): 8 full data reads over the whole job. The longest main-thread task was 298 ms.
- Real Chrome on this laptop's Intel UHD GPU, with memory free again:
  - Hub: 3D active, 58–60 fps, no context loss, no shader errors, no wasm errors.
  - Three rounds of Intake → Source → Review → Home: no context loss.
  - One frame of 300 ms on the first hover, in the development build.
